# GB Camera on the ESP32-P4X-EYE: plan

A pocket camera with three modes, cycled with the bottom button: **GB Camera** (128×112,
4 shades, the original camera's dithering/contrast/auto-exposure), **Dither Cam** (any of
32 palettes, 6 dither/error-diffusion methods, ported from the PIXEL CAM project), and
**Normal Cam** (plain colour preview). Photos saved to microSD.

Background research (other boards, sensors, cartridge ideas) is in [RESEARCH.md](RESEARCH.md).

**Status (2026-09-24):** firmware and PC tools written, including a full Dither Cam / Normal Cam mode and an on-screen menu, ported from the user's own [PIXEL CAM](../PIXEL%20CAM) project. Firmware and simulator build with no warnings from project code; all three PC accuracy tests pass (hardware style vs. the Pan Docs reference, PIXEL CAM style vs. `pixelboy/dither.py`, Dither Cam vs. `pixelboy/dithercam.py`). The PC simulator runs all three modes with a real webcam frame end to end. **Not yet run on the real board.**

### GB Camera mode

**Image pipeline, per frame:**
1. The ISP delivers a frame, RGB565 (falls back to GREY only if the sensor can't do colour).
2. Centre-crop to 8:7 and area-average (up to 4×4 samples) down to 128×112 luma.
3. Apply exposure as a digital gain.
4. Map onto the MAC-GBD voltage scale with `128 + (v − 128)/8`, which puts black at code 112 (1.5 V of 3.3 V).
5. Apply M64282FP edge enhancement on that scale (2-D, horizontal, or none, 50–500%).
6. Threshold against the 4×4×3 matrix built from gb-photo's contrast tables.
7. Output shades 0–3.
8. Run gb-photo's auto-exposure step on the result: a 12-tile histogram against the brightness target.

**Temporal noise reduction** (both styles, on by default at strength 2): after downscaling, each pixel moves a quarter of the way toward the new frame, but jumps straight there on changes of more than 24 levels, so motion doesn't smear. On a static scene with the webcam's measured noise, flicker dropped from 0.30% to 0.09% of pixels per frame (PIXEL CAM) and from 1.28% to 0.50% (hardware). Auto-levels also only switches curves when a new one is clearly better (+0.03 bits), and snaps once converged.

**Two styles** share steps 1, 2 and 6 (the ROM threshold dither):
- **PIXEL CAM** (default, `gbcam_pixelcam.c`): a port of the PIXEL CAM project's GB mode. It uses a contrast pivot plus gamma, then `128 + gray/2`, with levels auto-picked by trying 35 contrast/gamma pairs and keeping the one with the highest shade entropy (smoothed per frame, cached candidate LUTs so the ESP32-P4's software `pow()` only runs once). There's no edge enhancement, and the light table follows mean brightness. Brightness biases gamma. Pixel-identical to `pixelboy/dither.py` for fixed levels (`test_pixelcam.py`). On one webcam frame, the auto-levels matched the original's choice exactly.
- **HARDWARE:** steps 3–8 above. Switch with a long press on Mode.

**Accuracy (hardware style):** steps 3–7 are pixel-identical to the Pan Docs reference emulation (Antonio Niño Díaz / GiiBiiAdvance). At contrast 7, the dither registers match the real Game Boy Camera ROM's byte for byte, for both light tables (Raphael Boichot's register logs). The per-light-level edge modes and tables follow the stock camera's five register sets. Run `python tools\host\test_reference.py` to check all of this.

**Screen layout:** the 2× image is 224×224 (source columns 8–119 of 128); a 16 px dark border on the left holds the vertical brightness bar, and a 16 px border along the bottom holds the horizontal contrast bar, both drawn in the palette's own shades with round end caps and a knob, like the real camera's shooting screen.

### Dither Cam and Normal Cam modes

Ported from the PIXEL CAM project (`dithercam.c`, from `pixelboy/dithercam.py` and
`xiao-pixelcam/src/dithercam.cpp`): centre-crop to the target aspect, nearest-neighbour
downscale (Dither Cam) or box-average downscale (Normal Cam's smoother preview), an
optional contrast/gamma pivot, then nearest-colour matching against the chosen palette
(weighted distance `2·dr² + 4·dg² + 3·db²`) with an optional dither: **None**, **Bayer
4×4**, **Bayer 8×8**, **Floyd-Steinberg**, **Atkinson** or **Sierra Lite** (the last three
are real error diffusion). 18 GB-style 4-colour palettes and 32 Dither Cam palettes (up to
64 colours each), generated from the PIXEL CAM project's own exports by
`tools/gen_palettes.py` — rerun it if those change.

**Output sizes are exactly PIXEL CAM's own presets** (`pixelboy/dithercam.py`
`RESOLUTIONS`), so a photo taken here matches one taken on the Android/Pi app at the same
setting: 32×24, 64×48, 128×96 (default), 256×192, 320×240, 256×128. The photo is always
captured and quantized at the full size chosen. On screen, `display_begin_camera()`
(`app_display.c`) shows it two ways: the three that fit the 240×240 LCD (32×24 up to
128×96) are shown pixel-perfect, nearest-neighbour upscaled by the largest integer factor
that still fits, so the pixel art stays sharp-edged; the three that don't (256×192 and
up) are shown as a smaller, box-averaged, same-aspect-ratio **representation** instead —
a preview only, not what gets saved. Normal Cam always uses the 320×240 preset
(`DC_NORMAL_SIZE_INDEX`) with no quantizing, just the contrast/gamma pivot; being wider
than 240 px, it also goes through the representation path, landing at 240×180.

**Accuracy:** pixel-identical to `pixelboy/dithercam.py`'s pure-Python reference quantizers
across 4 palettes × 6 methods × 2 test images (`test_dithercam.py`); the tiny remaining
differences (worst case 0.10%) are float32-vs-float64 rounding late in an error-diffusion
chain, the same kind of gap `test_pixelcam.py` sees.

### Controls, menu and photo storage

See [README.md](README.md#controls) for the full control table and photo file layout.
In short: the encoder press is now the shutter (it's a push-button on the P4X-EYE's
encoder); the bottom button cycles the three camera modes; the top button opens an
on-screen menu of the current mode's settings, or (long press) the gallery.

**The gallery shows every photo from every mode in one list**, oldest first. GB Camera
and Dither Cam/Normal Cam photos share a single numbering sequence (`app_storage.c`'s
`s_next_number`) precisely so a combined, sorted list is correct without needing a
separate merge step. GB Camera photos load back from their `.BIN` tiles as before;
Dither Cam/Normal Cam photos have no tile form, so the gallery decodes the saved
`DCnnnnn.PNG` back with a new PNG-only build of stb_image (`components/stb/stb_image_impl.c`,
`STBI_ONLY_PNG` to keep code size down) and displays it with the same fit-or-shrink logic
`display_begin_camera()` already used for their live preview.

**Found and fixed a real bug while testing this:** `BTN_MENU` was included in the
gallery's "leave on press" condition, so pressing Menu at all pre-empted its own click
before the delete-confirm logic could ever run — deleting a photo via Menu had been
silently impossible since Menu took over the gallery-exit role. Fixed to match the
documented control table (Shutter press or a Menu *long* press leave the gallery; a
plain Menu click is only ever the delete arm/confirm).

## Performance on the ESP32-P4 (estimated; measured on first boot)

There's no ESP32-P4 simulator. Espressif's QEMU only emulates the ESP32, ESP32-C3 and ESP32-S3, and isn't cycle-accurate anyway. So these are estimates from operation counts, cross-checked against the PC timings (the simulator does ~0.5 ms/frame on a PC, and the P4 is very roughly 40–100× slower on this code). The firmware logs the real numbers every 60 frames: `fps | wait, downscale, process, draw`.

| Stage, per processed frame | Estimate | Notes |
|---|---|---|
| Downscale (1080p RGB565 → 128×112, 4×4 samples) | ~10–20 ms | Dominant cost: PSRAM reads plus RGB→luma. 8×8 samples would be ~4× slower, which is why the board uses 4×4 (`gs.max_samples = 4`) |
| PIXEL CAM process (35-candidate search + dither) | ~4–6 ms | Candidate curves are cached. They were being rebuilt every frame with **software double-precision `pow()`** (the P4's FPU is single-precision only; the ELF showed `pow`, `__muldf3`, `__divdf3`), which would have cost an estimated 70–200 ms/frame |
| HARDWARE process | ~1–2 ms | |
| Denoise | <0.5 ms | |
| Draw (compose) | ~1–2 ms | The SPI transfer (~11.5 ms at 80 MHz) runs by DMA in the background |

At **15 fps** (`TARGET_FPS` in `app.c`) that's roughly 30–45% of one of the two cores, leaving room for saving photos, Wi-Fi and so on. At 30 fps it would be tight. Pacing only reduces CPU work; the sensor, ISP and MIPI link still stream at the sensor's own rate. To save more power, set the OV2710 itself to a 15 fps mode, if its esp_cam_sensor driver offers one (M3). A lower frame rate also allows longer, flicker-safe exposures (50 ms is a whole number of mains light pulses for both 50 Hz and 60 Hz).

## ESP32-C6 on the board

The ESP32-P4 has no radio. The **ESP32-C6-MINI-1U** is its Wi-Fi 6 / Bluetooth 5 (LE) co-processor, connected over SDIO and running Espressif's **esp-hosted** firmware. The P4 uses it through the `esp_wifi_remote` + `esp_hosted` components, as if Wi-Fi were built in. Its enable pin is GPIO9 in the factory BSP, and it has its own test points for reflashing.

It's not suited to image processing (single-core 160 MHz RISC-V, no PSRAM, behind an SDIO link), but it's useful for:
- **Bluetooth LE to the PIXEL CAM Android app.** That app already has `PixelCamBleClient` / `PhotoTransferAssembler`. The camera could speak the same BLE photo-transfer protocol.
- **BLE thermal printers.** The Android app has `ThermalPrinterClient` / `ThermalPrinterProtocol`, so the camera could print directly, a modern Game Boy Printer.
- **Wi-Fi:** a small web gallery to download photos, or OTA firmware updates.

## Known issues and decisions

- **Paths with spaces.** ESP-IDF can't build in `D:\DEV TOOLS\GB CAMERA RP` (the camera tuning config script splits paths on spaces). `tools\fw.ps1` mirrors the project to `C:\esp\gbcam_build` and builds there. Moving the project to a path without spaces would remove the need for this.
- **BSP choice.** `espressif/esp32_p4_eye_noglib` 2.0.1 and 2.0.2 don't compile (they reference `lv_indev_t`), so we use `espressif/esp32_p4_eye`. LVGL is compiled in but never started.
- **Two BSP sources.** The official esp-bsp package defines only the Boot button (GPIO35). The 3 user buttons and the encoder push come from Espressif's factory-demo BSP (esp-dev-kits). We drive the buttons directly with GPIO + PCNT.
- **Exposure tiers.** These normally follow the sensor's real exposure time. We only know our digital gain, which the ISP's auto-exposure keeps near its middle value, so the viewfinder usually sits in tier 1 (2-D edge, "high-light" table), the typical daylight look.
- **Sensor model (fixed 2026-09-24).** The first version used a guessed `0x80 + luma/2` mapping and sharpened before it. It's now the reference model, verified by `tools/host/test_reference.py`. The default contrast is 7 because that matches the stock registers (gb-photo's default is 8). One deliberate deviation: the reference clamps horizontal-edge output to 0..255 on signed values, which looks like a slip; we use the same symmetric clamp as 2-D mode.
- **What can't be 1:1.** The OV2710 isn't the M64282FP. Its colour response, infrared sensitivity, noise and lens all differ, and the ISP's own auto-exposure runs first, so exposure tiers come from our digital gain rather than the real exposure time.
